# Независимая проверка изменений хранения

Проверены изменения `api/main.py`, `api/forecast_store.py`, новый `tests/test_api_storage_contention.py` и существующие тесты архива/API. Блокирующих или существенных регрессий в рассмотренном изменении не обнаружено. Исходники не менялись; отдельные тесты, серверы и нагрузки в рамках этого review не запускались, чтобы не влиять на текущую серию измерений. Хеши рассмотренных файлов и машинные проверки receipt сохранены в `storage_review.json`.

## Подтверждённое по коду

- `ensure_journal_schema()` на уже подготовленной БД проверяет необходимые колонки через `PRAGMA table_info` и возвращается без `BEGIN IMMEDIATE`. Таким образом, GET больше не резервирует единственного SQLite-писателя только ради проверки миграции. Чтение схемы само по себе не отменяет обычные правила блокировок SQLite.
- Первая и legacy-миграция остаются внутри `BEGIN IMMEDIATE`. После захвата блокировки повторно проверяются колонки tickets, поэтому два параллельных первых запроса не пытаются дважды добавить одну колонку. Создание feedback идемпотентно. Канальные черновики сохраняются, новые поля получают прежние defaults.
- `connection()` по-прежнему фиксирует успешную операцию, откатывает неуспешную через `with conn`, а в `finally` закрывает соединение. Схема коммитится отдельно до пользовательской вставки; отказ вставки не должен удалять уже завершённую миграцию.
- Процессного кэша признака «схема готова» нет: каждое новое соединение проверяет именно открытую БД. Восстановление закрытой БД между запросами не оставляет такой кэш устаревшим.
- `load_run_with_metadata()` возвращает оба значения существующего `_read_one()` за один вызов. Payload и metadata получены из одной строки одного SELECT; payload по-прежнему проверяется по checksum, canonical JSON, контракту времени/цели, metadata и индексным полям. Ни одна из прежних проверок не удалена.
- `dataset()` использует эту пару вместо двух независимых чтений. Ошибки отсутствующего выпуска/режима по-прежнему преобразуются в 404, повреждения архива — в 503. Legacy JSON-ветка не изменена; рекомендации и исходные карточки вычисляются прежним кодом.

## Содержательность тестов и имеющиеся свидетельства

Прочитаны результаты, полученные root, без повторного запуска:

| Проверка | Что действительно проверяется | Результат сохранённого запуска |
|---|---|---|
| Чтение при удерживаемом RESERVED lock | Писатель меняет note без commit; другой GET должен прочитать прежний committed note, а не ждать собственного writer-reservation | Baseline: `database is locked`; optimized: pass |
| Одновременное первое использование | 24 вставки в ещё пустую БД через 12 потоков, итоговое число и `integrity_check` | Pass |
| Legacy tickets | Старая канальная запись/заметка сохраняются; новые entity_mode/snapshot получают defaults | Pass |
| Ошибка внутри записи | Исключение после INSERT откатывает запись; схема остаётся пригодной | Pass |

Сохранённые логи: `baseline_contention_tests.log` — 4 теста, ожидаемый один отказ в проверке RESERVED lock; `optimized_contention_tests.log` — 4/4; `full_tests.log` — 170/170. Существующие API/store-тесты также проверяют metadata/checksum, повреждённый архив, неправильный режим, сохранность снимков и отсутствие отката на legacy при ошибке. Статический review не приписывается независимому повторному запуску этих тестов.

## Границы и оставшиеся риски

- Успех при RESERVED lock не означает отсутствие ожидания при EXCLUSIVE lock или при конкурирующих записях. SQLite по-прежнему имеет одного писателя и timeout 30 секунд; WAL/workers/indexes не изменены.
- Проверка готовности схемы сравнивает имена колонок, а не полную схему/ограничения. Поддерживаются текущая схема и известная legacy-схема tickets; произвольное повреждение таблиц, неизвестная старая схема feedback или внешние DDL здесь не исправляются. Данное ограничение уже существовало и не является новой регрессией.
- Отсутствие process-cache не делает безопасной замену SQLite-файла во время открытых соединений. Горячая замена, некорректное копирование WAL и конкурирующее внешнее редактирование остаются вне проверенного режима.
- Тест чтения вызывает функцию API непосредственно; HTTP/ASGI-производительность проверяется отдельным harness. Размер ускорения из функционального теста вывести нельзя.
- Проверяемые изменения сокращают лишнюю блокировку миграции и повторную проверку выпуска. JSON-проверка оставшегося чтения, создание рекомендаций для 78 карточек и неограниченный список tickets остаются; заявление «без деградации при 20 клиентах» требует фактических результатов сопоставимого trace.

## Исправление scope integrity

Замечание о misleading field закрыто: имя `final_snapshot_cards_recommendations_and_six_payloads_exact` заменено на `final_snapshot_cards_and_six_payloads_exact`. Независимо проверены SHA после исправления и восстановленные SHA до исправления для всех девяти файлов из `claim_correction.json`; механическая обратная замена единственного имени поля воспроизводит прежние байты. Также проверяется, что хеш исходного harness из baseline воспроизводится обратной заменой имени поля в текущем harness. Тайминги/операции/валидаторы при этом не менялись.

Формулировка теперь соответствует выполненной проверке точных карточек и шести payload. Полного совпадения всех полей рекомендаций harness не доказывает; ограничение не закрыто переименованием и не скрывается в данном review.
