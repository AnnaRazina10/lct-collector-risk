# Независимая проверка рекомендаций

Проверены 6 реальных выпусков / 468 карточек. Все рекомендации status=ok; 1981 проверка выполнена. API через TestClient работал с отдельной временной SQLite; рабочие решения не читались и не менялись.

Срабатывания: {'PARTIAL_CATALOG_RECORDS': 276, 'ALARM_RECORDED_TODAY': 86, 'MULTIPLE_ALARM_DAYS': 170, 'NO_RECORDS_TODAY': 190}. Сочетаний правил: 6; различных текстов шагов: 129. Две запасные ветви SELECTED_FOR_REVIEW и OUTSIDE_WARNING_POLICY отсутствуют в этих реальных карточках и проверены отдельно на синтетических данных.

Исходные payload, content hashes, score, warning и rank шести выпусков сохранились. В каждом onset-выпуске остались ровно первые 10 объектов по score descending / object_id ascending. Будущие поля не используются: модуль отвергает их, API передаёт только allowlist; добавление будущих полей и изменение score не меняют рекомендации при тех же разрешённых фактах.

Карточки detail, feedback и ticket получают рекомендации из серверного выпуска. Поддельные client recommendation/facts/snapshot проигнорированы. Старые snapshots с рекомендацией и без неё не пересоздаются при чтении журнала; повторный черновик сохраняет прежний снимок. Никакой внешней отправки нет.

Тексты предлагают проверить поступление данных, тревожные записи и предыдущую отработку; не назначают ремонт и не утверждают физическую причину. Частичный текущий каталог не назван неисправностью. Исторические факты отделены от времени применения правил.

Небольшое замечание к UI исправлено root и независимо перепроверено: подпись теперь отдельно называет cutoff наблюдений и время определения очереди при выпуске. API/store/rules со времени полного прогона не менялись. Открытых замечаний нет; проверяющий код продукта не редактировал.

Все численные и поштучные доказательства, SHA и правила перечислены в independent_review.json. Проверка не подтверждает полезность рекомендаций для предотвращения физических отказов; такой эффект требует диспетчерской оценки.
