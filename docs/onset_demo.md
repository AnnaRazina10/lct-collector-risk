# Архивная очередь «Начало серии»

В объектном режиме доступны две разные цели. По умолчанию открывается прежняя «Любая тревога». Выбор «Начало серии» открывает последний сохранённый выпуск исследовательской модели этой цели; список выпусков содержит только соответствующие ей расчёты. При прямой ссылке с `run_id` цель определяется по сохранённому выпуску. Канальная демонстрация остаётся отдельным режимом.

Для текущего локального сервера:

- Обычный вход: `http://127.0.0.1:8781/`.
- Последний выпуск начала серии: `http://127.0.0.1:8781/?mode=object&target=registered_episode_start_g1`.
- Конкретный выпуск: `http://127.0.0.1:8781/?mode=object&run_id=<идентификатор_выпуска>`.

Если выпусков начала серии пока нет, интерфейс сообщает об их отсутствии. Прогноз другой цели вместо них не подставляется. Неизвестный идентификатор выпуска остаётся ошибкой.

## Смысл очереди

На момент исторического выпуска D+1 00:00 доступны записи по день D включительно. Цель — отсутствие зарегистрированной тревоги в день D+1 и наличие тревоги в день D+2. День D+1 ещё неизвестен при выпуске. До начала целевого дня остаётся 24 часа.

Название обозначает начало зарегистрированной серии после календарного дня без тревожных записей. Физический отказ такой разметкой не подтверждается. Отсутствие записей не означает исправность или полное покрытие датчиков. Наличие записи тоже не гарантирует наблюдаемость всех каналов.

В каждом выпуске выбираются ровно 10 объектов. Политика хранится в `warning_policy`: `daily_top_k`, `k=10`, `tie_break=score_desc_object_id_asc`. Порядок задают score по убыванию и строковый идентификатор объекта при равенстве score. Интерфейс использует сохранённые `card.rank` и `card.warning`; значение `threshold` не определяет включение при равных оценках и не показывается как правило выбора для этой цели.

Очередь формируется заново каждый день. Один объект может попадать в неё подряд; подавление повторных предупреждений и период ожидания после проверки не реализованы. Фильтры поиска, отсутствия тревоги в день признаков и выбранных объектов меняют только отображение сохранённых карточек, а не состав очереди.

Score служит для ранжирования и не является откалиброванной вероятностью поломки. Для новой модели показываются наблюдения из доступной истории (`explanation_kind=observations`), без графиков вкладов признаков и заявлений о причине события. Старые показатели качества цели «Любая тревога» не переносятся в новую очередь.

## Выпуски и решения

Карточка и форма действий показывают цель, место в очереди и идентификатор выпуска. Черновик заявки и решение отправляют прежние поля `risk_id`, `entity_mode`, `run_id`; API сохраняет снимок соответствующего неизменяемого выпуска. В журнале отображаются цель, rank, run_id и окно прогноза из этого снимка.

Журнал по умолчанию показывает среди загруженных записей текущий режим и цель. Флажок «Все режимы» открывает записи разных целей с явными подписями. Фактическое время сохранения отделено от времени исторического выпуска. Черновики и решения остаются локальными; сообщения внешним системам не отправляются.

Сохранённые выпуски не содержат исходов целевого окна. Кнопки раскрытия архивного исхода для них нет; исходы не загружаются из другого архива. В прежней исходной демонстрации отдельная кнопка проверки архивного факта сохраняется.

При переключении режима, цели или выпуска увеличивается номер поколения загрузки. Ответы прежних запросов не заменяют новый экран. Формы фиксируют карточку, режим и выпуск до отправки; ответ запоздавшей операции не обновляет экран другого поколения. Журнал дополнительно защищён собственным номером запроса.

## Проверка интерфейса

Синтаксис встроенного JavaScript проверен через `node --check`. Реальная проверка в Codex in-app browser завершена: переключение целей/выпусков, ранги 1/11, фильтр 10 объектов, схема групп, тестовый черновик и решение, журнал и прямая ссылка. Снимки двух тестовых записей дополнительно проверены в локальной SQLite. Итог: `reports/onset_demo/ui_check.json`. Быстрые ответы с управляемыми задержками проверены отдельно в Node VM, а не имитированы вручную в браузере. Повторяемый сценарий:

1. Открыть обычный вход: выбрана «Любая тревога», доступны исходная демонстрация и только её сохранённые выпуски.
2. Выбрать «Начало серии»: автоматически открывается последний выпуск; в списке только три onset-выпуска текущего тестового архива. Видны 78 объектов, 10 выбранных, 24 часа и явное описание исследовательского архивного сценария.
3. Проверить места 1 и 11, фильтр выбранных объектов, схему групп и определения D/D+1/D+2. Отсутствуют пороговая формулировка для отбора, графики вкладов и кнопка исхода.
4. В отдельной тестовой базе сохранить черновик и решение с пометкой «ТЕСТ интерфейса, не операционное действие» и оператором «ТЕСТ». В журнале проверить цель, место и тот же run_id.
5. Переключиться на другую дату onset, затем на «Любая тревога» и каналы. Убедиться, что карточки и подписи соответствуют выбору; старый канал и его архивная проверка работают.
6. Открыть прямую ссылку с onset `run_id` без параметра цели: цель должна автоматически стать «Начало серии». Повторить быстрые переключения и проверить, что запоздавшая загрузка не подменяет выбранный выпуск.

Сценарий не подтверждает работу промышленного потока, оперативный SLA или прогноз физических отказов. Новой моделью прежний рабочий режим не заменён.

## Локальное воспроизведение

Нужны уже подготовленные `daily_2025.parquet`, `daily_2026.parquet`, справочники и замороженный `models/object_onset_experiment/refit/hurdle_15.joblib`. Данные, веса и SQLite не входят в Git; один clone без этих файлов не воспроизводит ML-прогноз. Контрольные суммы проверяются до загрузки модели. API использует только сохранённые выпуски и не обучает модель.

Из корня репозитория с установленным окружением:

```sh
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 .venv/bin/python src/serving/object_onset_forecast.py
LCT_TICKET_DB="$PWD/data/app/onset_demo.sqlite3" .venv/bin/python -m uvicorn api.main:app --host 127.0.0.1 --port 8781
```

Команда producer по умолчанию рассчитывает 26–28 июня 2026 и повторно публикует те же данные идемпотентно. В текущую тестовую базу также скопированы три ранее проверенных any-alarm выпуска для проверки переключений; producer их сам не создаёт. Исходные JSON-демонстрации формируются прежними экспортерами, описанными в `object_demo.md` и `local_demo.md`.

Веса используют исходы по 30 ноября 2025. Декабрьская проверка кандидата заканчивается 31 декабря; поэтому исторический выпуск разрешён только с 1 января 2026. Итоговые метрики и решение по периоду 2026 не читаются producer и не приписываются прошлому. Время фактического создания записи — `archive_metadata.created_at`, историческое время — `issue_time`.

Замер трёх выпусков: 1,91–1,95 секунды от чтения очередного дневного агрегата до сохранения. Первичная загрузка модели и bootstrap-истории исключены; задержка исходного потока не измерена. Независимая проверка на двух датах дала точное совпадение всех 78 оценок с сохранённым экспериментом и 37 пройденных проверок. Семь воспроизводимых сценариев задержанных ответов: `node tests/test_web_async.js`; общий Python-прогон: `.venv/bin/python -m unittest discover -s tests -v`.
