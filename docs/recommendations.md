# Локальные рекомендации диспетчеру

Состояние на 29.09.2026: рекомендации реализованы в [чистом модуле](../src/serving/local_recommendations.py), [API](../api/main.py) и [интерфейсе](../web/index.html). Для сохранённых объектных выпусков карточка показывает раздел «Что проверить диспетчеру»; новое локальное решение или черновик хранит снимок рекомендации. Прогнозы, порядок очереди и исходные архивные карточки не пересчитываются.

Проверено на шести реальных исторических выпусках, 468 карточках, с отдельной временной SQLite для тестовых записей. [Независимый отчёт](../reports/recommendations/independent_review.md) и [машиночитаемые доказательства](../reports/recommendations/independent_review.json) содержат 1 981 пройденную проверку; открытых замечаний нет. Дополнительно [отдельный отчёт](../reports/recommendations/http_restart.json) подтверждает явное тестовое сохранение через браузер, отображение рекомендации в журнале и чтение после реального перезапуска сервера.

В компактный офлайн-комплект полный каталог исследовательских `reports` не включается. Относительные ссылки на отчёты и скриншоты выше и ниже рассчитаны на полный checkout. Полные доказательства находятся в [каталоге reports/recommendations репозитория](https://github.com/AnnaRazina10/lct-collector-risk/tree/main/reports/recommendations); доступ требует предоставленных прав к репозиторию.

## Назначение и границы

Тексты предлагают проверить поступление данных, зарегистрированные тревоги и предыдущую отработку. Они не определяют причину неисправности, не назначают ремонт, не управляют оборудованием и не отправляют заявки. Окончательное решение принимает диспетчер.

Правила применяются сейчас к архиву. `generated_at` — фактическое UTC-время формирования ответа/снимка; исторический `issue_time` остаётся временем выпуска исходного прогноза. Применение правил в историческую дату не подтверждается. Рекомендации не превращают score в вероятность физической аварии и не улучшают измеренные метрики модели сами по себе.

## Чистый программный контракт

```python
from src.serving.local_recommendations import recommend, RecommendationValidationError

result = recommend(facts, context)
```

Функция принимает два `Mapping[str, object]` и возвращает JSON-совместимый `dict`. Она не обращается к файлам, БД, сети или часам. API собирает вход только из серверного выпуска и найденной в нём карточки. Клиентский текст, факты, рекомендации и снимки не служат источником для правил.

| Вход | Допустимые поля |
|---|---|
| `facts`, обязательные | `observed_channels`, `catalog_channels`, `events_today`, `alarm_channels`, `current_alarm`, `warning`, `alarm_days_7d`, `observed_days_7d` |
| `facts`, необязательное | `rank`, положительное целое, без пересчёта ранга |
| `context`, обязательные | `run_id`, `card_id`, `object_id`, `goal`, `mode`, `feature_date`, `feature_cutoff`, `issue_time`, `forecast_start`, `forecast_end` |

Цели: `any_alarm` и `registered_episode_start_g1`. Режим v1 — `historical_replay`. `card_id` должен равняться `run_id + '_' + object_id`; префикс выпуска — `object_` или `onset_` в соответствии с целью. Само существование выпуска, его целостность и совпадение выбранной карточки проверяет серверный архивный слой.

Дневной временной контракт: признаки по D 23:59:59 MSK, выпуск D+1 00:00, целевое окно D+2 00:00…D+3 00:00. До начала целевого окна — ровно 24 часа. Время без timezone и другие окна отклоняются; эквивалентные UTC timestamps нормализуются в MSK. Доступность исходных пакетов и модели проверяет producer; одни даты карточки не доказывают её.

Неизвестные поля, включая будущие исходы, `score`, `explanation` и произвольные сообщения, не допускаются в pure API. Неверный контекст вызывает `RecommendationValidationError`. Недостающие/противоречивые известные факты дают `status=insufficient_data`, диагностические коды и пустые шаги/evidence. `events_today` не имеет искусственного верхнего лимита. Нулевая наблюдаемость не означает исправность; неполный текущий каталог не означает отказ датчиков.

## Правила версии 1.0.0

| Код | Основание | Предлагаемая проверка |
|---|---|---|
| `NO_RECORDS_TODAY` | Ноль каналов с записями за D | Доступность источника и журнал поступления; состояние оборудования неизвестно. Правило исключает остальные шаги |
| `PARTIAL_CATALOG_RECORDS` | Записи есть лишь по части справочных каналов | Ожидаемый режим регистрации и полнота поступления |
| `ALARM_RECORDED_TODAY` | Уже есть тревожная запись за D | Сопоставление с журналом диспетчера и предыдущими решениями |
| `MULTIPLE_ALARM_DAYS` | Тревожные записи не менее чем в двух днях за семь календарных дней | Повторяемость и предыдущая отработка; число дней не называется числом аварий |
| `SELECTED_FOR_REVIEW` | Других оснований нет, объект выбран политикой предупреждений | Сопоставление наблюдений с журналом без вывода о подтверждённой поломке |
| `OUTSIDE_WARNING_POLICY` | Других оснований нет, объект не выбран | Отсутствие дополнительных оснований; отсутствие предупреждения не означает исправность |

Порядок фиксирован, максимум три шага. Текущая тревога не удаляет объект из onset-очереди: промежуточный D+1 неизвестен при выпуске. Правила не меняют порог, score, warning, rank, top-10, tie-break и не вводят подавление повторных предупреждений. Подробные условия и тексты приведены в [контракте](remaining_priorities.md#детерминированные-правила-и-текст).

Версия схемы результата — `1.0`. `ruleset_sha256` для проверенной версии:

```text
893f93b4c025d11ad605e18faaa1f3e37bd31e1c7cbcfeaeea08f6d40a72c4c7
```

Хеш описывает спецификацию, тексты и версию правил; он не является хешем всего исходного файла. `recommendation_id` детерминирован по контексту, разрешённым фактам и ruleset hash. Для одинакового входа чистый результат совпадает; меняющееся `generated_at` добавляет API отдельно.

Результат содержит `status`, нормализованный контекст, идентификатор рекомендации, версии и hash, `fact_cutoff`, `rule_ids`, `steps`, `evidence`, `validation_errors`, ограничения, `requires_dispatcher_decision=true` и `external_send=false`. У наблюдений `source='observation'`, `window_end=feature_cutoff`. У результатов политики `warning`/`rank` — `source='forecast_policy'`, `available_at=issue_time`, без `window_end`. Время принятия решения очереди не выдаётся за время наблюдения.

## HTTP и пользовательский путь

| Маршрут | Поведение |
|---|---|
| `GET /api/risks?mode=object&run_id=…` | Возвращает неизменные `cards` и отдельную карту `recommendations`, ключ — `card.id`. Чтение не сохраняет решение или черновик |
| `GET /api/risks/{risk_id}?mode=object&run_id=…` | Возвращает `forecast`, `card` и отдельный `recommendation` |
| `POST /api/feedback` | По `risk_id`, `entity_mode` и `run_id` сервер сам находит выпуск/карточку и сохраняет `risk_snapshot.recommendation` вместе с решением |
| `POST /api/tickets` | Аналогично сохраняет снимок с локальным черновиком; повторное создание возвращает первоначальный снимок |
| `GET /api/journal`, `/api/feedback`, `/api/tickets` | Читают сохранённые снимки; прежние рекомендации не пересоздаются при чтении |

API добавляет `generated_at` и `application_note` о сегодняшнем применении к архиву. При ошибке контекста возвращается `status=unavailable` с пустыми шагами, без падения основной карточки. Некорректные известные факты сохраняют статус `insufficient_data`. Старые режимы без `run_id` и канальная демонстрация используют прежнее поведение.

В UI раздел проверки показывает шаги, cutoff наблюдений, время определения очереди и версию правил. При нехватке данных выводится отдельное сообщение. В журнале отображаются сохранённые шаги, версия и фактическое время генерации. Имена операторов остаются локально введёнными, без подтверждённой корпоративной идентичности.

Существующие forecast payload и content hashes не переписываются. Старые решения без рекомендации остаются читаемыми. Пользователь сам нажимает сохранение; внешней отправки, автоматического назначения ремонта или смены статуса работ нет.

## Что именно проверено

- [151 Python-тест](../reports/recommendations/integration_tests.log) включает [22 теста чистого модуля](../tests/test_local_recommendations.py) и [API-сценарии рекомендаций](../tests/test_api_recommendations.py).
- [Семь сценариев Node](../reports/recommendations/web_async_check.json) проверяют фактический inline UI-код с минимальной имитацией DOM и управляемыми ответами fetch. Реального браузера, сети и записи в БД в этой проверке нет.
- [Независимый аудит](../reports/recommendations/independent_review.json): шесть реальных выпусков, 468 карточек, 468 уникальных recommendation IDs, все `status=ok`, 1 981 проверка. Сохранены исходные payload/content hashes, score, warning, rank и ровно top-10 каждого onset-выпуска.
- На этих карточках обнаружены шесть сочетаний правил и 129 различных текстов шагов. Числа срабатываний отдельных правил: частичная регистрация — 276, текущая тревога — 86, несколько тревожных дней — 170, отсутствие записей — 190. Одной карточке могут соответствовать несколько правил; сумма не является числом карточек. Две запасные ветви очереди проверены только синтетически.
- На отдельной временной SQLite через TestClient проверены серверное формирование снимка, игнорирование поддельных client facts/recommendation/snapshot, повторный черновик и неизменное чтение прежнего снимка после подмены текущей функции рекомендаций. Рабочие решения не читались и не изменялись. Новый TestClient не равен рестарту серверного процесса.
- [Реальная браузерная и restart-проверка](../reports/recommendations/http_restart.json), 29.09.2026 14:07 UTC: на отдельной `recommendation_demo.sqlite3` через браузер явно сохранено одно тестовое решение, показан его снимок рекомендации `NO_RECORDS_TODAY`. После остановки сервера и запуска нового процесса HTTP подтвердил полное совпадение журнала и метаданных шести выпусков. Ошибок консоли браузера — 0; внешней отправки и использования рабочей пользовательской БД не было. Скриншоты [сохранения](../reports/recommendations/ui_verified.png) и [журнала](../reports/recommendations/ui_journal_verified.png) визуально проверены. Проверка охватывает конкретный локальный сценарий, не все сочетания браузеров и инфраструктуры.

Локальный результат приближает сценарий §6/§18 ТЗ, но не подтверждает полную промышленную готовность.
