# Требования к решению

Уточнено 29.09.2026 по оригиналу [ТЗ 2026](<materials/8. ДЖКХ.pdf>) и его [постраничному тексту](materials/task08_extracted.txt). Ниже перечислены требования, а не подтверждения готовности реализации. Текущее состояние и ограничения приведены отдельно в [проверке готовности](readiness_audit.md) и [оставшихся приоритетах](remaining_priorities.md). Ранее в этой копии ошибочно были указаны обязательные Precision > 0.7 и Recall > 0.5; в §9 оригинала таких порогов нет.

## Функциональные требования

Сервис должен:

- анализировать исторические и текущие данные мониторинга СМВУ;
- обрабатывать журналы диспетчерской службы;
- использовать реестры оборудования и объектов;
- рассчитывать вероятность инцидентов с горизонтом не менее 24 часов;
- определять локацию оборудования или объекта в зоне риска;
- классифицировать тип прогнозируемого риска;
- показывать превентивные уведомления диспетчеру;
- формировать рекомендации по техническому обслуживанию;
- вести журнал прогнозов и результатов их отработки.

Создание черновиков заявок на ремонт относится к дополнительным требованиям, реализуемым по согласованию с Заказчиком ([§8, страницы PDF 8–9](<materials/8. ДЖКХ.pdf#page=8>)). Общие рекомендации по обслуживанию и ремонту остаются требованием §6.

Сервис не должен:

- заменять диспетчера;
- принимать окончательное решение об инциденте;
- управлять инженерным оборудованием напрямую;
- выполнять ремонтные работы.

## ML-требования

- Горизонт прогноза: не менее 24 часов.
- Целевые Precision и Recall определяются на этапе проектирования исходя из качества предоставляемых данных (§9).
- Порог предупреждения и допустимую нагрузку на диспетчера обосновать на временной проверочной выборке. Значения0.7/0.5 в старых экспериментах — дополнительный инженерный ориентир, не обязательные условия ТЗ.
- Прогноз должен иметь вероятность, тип риска и интерпретируемое объяснение.
- Проверка качества должна выполняться на временном разбиении, чтобы не допустить
  утечки будущей информации в обучение.

## Требования к производительности

- Время формирования прогноза для одного объекта: не более 300 секунд.
- Обработка потоковых данных: близко к real-time, задержка не более 300 секунд.
- Система должна поддерживать не менее 20 одновременных пользователей без
  деградации производительности.

Основание: [§§9–11, страницы PDF 9–10](<materials/8. ДЖКХ.pdf#page=9>).

## Пользовательский интерфейс

Минимальный интерфейс диспетчера:

- аналитическая панель с уровнями риска;
- список объектов и датчиков, отсортированный по приоритету;
- карточка риска с вероятностью, горизонтом, типом датчика и объяснением;
- интерактивная карта объектов инфраструктуры с выделением проблемных зон ([§10, страница PDF 9](<materials/8. ДЖКХ.pdf#page=9>)); схема без географических координат не заменяет это требование;
- журнал прогнозов и фактических решений;
- уведомления о критических инцидентах;
- экран или модальное окно для формирования черновика заявки — дополнительный интерфейс MVP для функции §8, по согласованию с Заказчиком.

UI должен быть интуитивным: логически связанные блоки размещаются рядом, а каждый
элемент экрана должен помогать конкретному сценарию пользователя.

## REST API

Предложенные эндпоинты MVP ниже — проектные решения, а не буквальный перечень маршрутов из ТЗ и не описание всех уже реализованных маршрутов. [§10](<materials/8. ДЖКХ.pdf#page=9>) требует REST API для получения данных из внешних систем.

```text
GET  /health
POST /predict
GET  /risks
GET  /risks/{risk_id}
POST /tickets/draft
POST /feedback
GET  /objects
GET  /sensors
```

Пример назначения:

- `/predict` - запустить расчет прогноза по объекту, датчику или временному окну;
- `/risks` - получить текущую очередь рисков;
- `/tickets/draft` - сформировать черновик заявки на превентивное обслуживание;
- `/feedback` - сохранить решение диспетчера по прогнозу.

## Интеграция и данные

Раздел13 оригинала прямо предусматривает внешние метеоданные через открытыеAPI (температура, влажность, осадки, давление) и нормативный РТЭК. Для погоды необходимо указать источник, пространственное приближение и доступность информации на момент прогноза. Разрешение на произвольное внешнее обучение из этого не следует.

Поддерживаемые форматы:

- CSV/XLSX для исторических файлов;
- JSON/XML для программного обмена;
- поддержка подключения к PostgreSQL или иной СУБД, используемой в инфраструктуре ([§7, страница PDF 8](<materials/8. ДЖКХ.pdf#page=8>)); отдельно §11 требует для серверной СУБД PostgreSQL 12 и выше;
- GeoJSON/WKT для геоданных ([§7](<materials/8. ДЖКХ.pdf#page=8>)).

Интеграция с внутренними системами заказчика должна выполняться в режиме read-only.

## Безопасность и надежность

- TLS 1.2 или выше для шифрования данных при передаче.
- Аутентификация пользователей с поддержкой интеграции с корпоративной службой каталогов LDAP/AD.
- Разграничение прав доступа на основе ролевой модели (RBAC).
- Журналирование всех действий пользователей в системе.
- Автоматическое создание резервных копий данных.
- Целевое время восстановления после сбоя: не более 4 часов.

Основание: [§11, страница PDF 10](<materials/8. ДЖКХ.pdf#page=10>). Оговорка о переносе этих требований только в будущую промышленную версию в оригинале отсутствует.

## Инфраструктура

- Серверная часть: Linux.
- Браузеры: актуальные версии Google Chrome и Яндекс.Браузера.
- СУБД: PostgreSQL 12 и выше.

Основание: [§11, страница PDF 10](<materials/8. ДЖКХ.pdf#page=10>). Возможность обмена с другой СУБД в §7 не отменяет указанное требование совместимости серверной части.
