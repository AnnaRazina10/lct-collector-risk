# Резервная копия и восстановление локальной SQLite-базы

`scripts/database_backup.py` создаёт проверяемую копию локальной SQLite-базы и восстанавливает её **только в новый путь**. Рабочая пользовательская база при разработке и проверке не открывалась. Проверки выполнены на синтетической базе и отдельной настоящей базе исторического replay с тремя выпусками прогнозов, на macOS 15.3.1 arm64, Python 3.12.14, SQLite 3.53.1; нужны только модули стандартной библиотеки Python.

## Команды

Укажите фактический путь из `LCT_TICKET_DB`. Если переменная не задана, существующий API использует `data/app/tickets.sqlite3`. Пример создания новой копии из корня проекта:

```bash
.venv/bin/python scripts/database_backup.py backup --source data/app/tickets.sqlite3 --destination /private/tmp/lct-backup-20260929
.venv/bin/python scripts/database_backup.py verify --bundle /private/tmp/lct-backup-20260929
```

Каталог назначения не должен существовать. Результат — пара `database.sqlite3` + `manifest.json`, опубликованная как один каталог после всех проверок. Штатный [SQLite Online Backup API](https://www.sqlite.org/backup.html) читает согласованное состояние базы, включая зафиксированные данные в WAL; обычное копирование одного рабочего `.sqlite3` для этого не используется. Python предоставляет этот механизм как [`Connection.backup`](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup).

Восстановление в отдельный новый файл:

```bash
.venv/bin/python scripts/database_backup.py restore --bundle /private/tmp/lct-backup-20260929 --destination /private/tmp/lct-restored-20260929.sqlite3
```

Перезапись запрещена: нет флага `--force`. Команда откажется работать, если файл, каталог, символическая ссылка либо `-wal`, `-shm`, `-journal` выбранного имени уже существует. Рядом с назначением создаётся временный файл, проверяется, синхронизируется и атомарно переименовывается. Отказ действует и при конкурентном появлении самого файла назначения: на macOS используется `renamex_np(RENAME_EXCL)`, на Linux — `renameat2(RENAME_NOREPLACE)`. Обычный POSIX `rename` способен перезаписывать файл, поэтому проверки только через `exists()` недостаточно. [Apple: exclusive rename](https://developer.apple.com/documentation/foundation/urlresourcevalues/volumesupportsexclusiverenaming), [Linux: renameat2](https://man7.org/linux/man-pages/man2/rename.2.html).

Неподдерживаемый вариант файловой системы/платформы даёт ошибку вместо небезопасной перезаписи. Linux-ветка и контейнерный запуск пока не исполнялись; проверен macOS no-replace primitive. При ошибке удаляются только принадлежащие вызову временные файлы; уже существовавшие файлы не удаляются. Если ошибка синхронизации каталога произошла после завершённого rename, опубликованный проверенный файл сохраняется: команда может вернуть ошибку, поэтому состояние следует проверить, а не удалять автоматически.

Каждая команда выводит JSON и код завершения 0 при успехе, 1 при отказе/повреждении. Общий лимит проверок задаётся `--timeout`, по умолчанию 60 секунд; проверки времени выполняются в цикле копирования и сканирования. Время отдельных системных операций и сортировки больших наборов не является жёсткой real-time гарантией.

## Что именно сохраняется и проверяется

- Схема `main`: пользовательские и внутренние таблицы, индексы, представления, триггеры; неизвестные заранее таблицы включаются автоматически.
- Все столбцы и строки, включая JSON-снимки карточек и прогнозов, решения диспетчера, BLOB, `NULL`, целые, дробные значения и Unicode-текст. Для каждой таблицы проверяются число строк, метаданные столбцов и SHA-256 канонических типизированных строк; порядок хранения строк не влияет на результат, повторы учитываются.
- Внутренняя `sqlite_sequence`, `user_version`, `application_id`, кодировка. Тест также проверяет продолжение autoincrement и исполнение сохранённого триггера после восстановления.
- `PRAGMA integrity_check` исходного снимка, готовой копии и восстановленной базы должен дать `ok`. Схема/число строк/хеши содержимого должны совпасть между снимком источника и копией, затем между копией и восстановлением.
- `manifest.json` содержит версию формата, время, режим журналирования источника, размер и SHA-256 файла копии, схему и хеши строк. `verify` и `restore` сверяют размер/контрольную сумму до чтения, затем логическое содержимое. Восстановление повторно проверяет, что файл копии не изменился во время операции.

Копия переводится в самостоятельный `journal_mode=DELETE`; работающему источнику режим не меняется. Готовой копии не требуются соседние WAL-файлы. Восстановленный файл может иметь другую байтовую контрольную сумму из-за заголовка SQLite; соответствие доказывается отдельными проверками схемы и содержимого, а новый SHA-256 выводится в результате.

Чтение источника удерживает одну read transaction с момента первого чтения схемы. Изменения, зафиксированные после этого момента, в выбранный снимок не входят. В WAL тест подтвердил возможность параллельного commit другого writer во время копирования. Длительная read transaction может задержать очистку WAL; в rollback/delete режиме она также может задерживать commit писателей. На больших базах нужен отдельный замер длительности и влияния на рабочую нагрузку. Проверка хешей хранит отсортированные 32-байтовые digest всех строк одной таблицы с накладными расходами Python; память растёт с размером таблицы.

## Подключение восстановленной базы к отдельному API

Сначала завершите `restore` и проверьте успешный JSON-результат. Для проверки запустите отдельный экземпляр API на свободном порту, явно указав новый путь:

```bash
LCT_TICKET_DB=/private/tmp/lct-restored-20260929.sqlite3 .venv/bin/python -m uvicorn api.main:app --host 127.0.0.1 --port 8770 --workers 1
```

Проверьте `/api/health`, `/api/tickets?mode=object`, `/api/feedback?mode=object`, `/api/journal?mode=object` и сохранённые снимки. Такой запуск не переключает ранее работавший процесс API: переменная читается при старте. Не назначайте резервную копию внутри bundle рабочей базой — восстановите отдельный файл. Новые изменения после запуска будут записываться именно в восстановленную базу.

Утилита копирует только одну SQLite `main` database. Архивные карточки `data/app/*.json`, модели, исходные журналы, настройки и базы, подключённые через `ATTACH`, в эту копию не входят. Для запуска демонстрации JSON-файлы по-прежнему нужны отдельно. Автоматическое переключение сервиса и проверка HTTP через восстановленный файл в этом упражнении не выполнялись; напрямую проверены сохранённые данные и работа SQLite после восстановления.

## Фактически выполненное упражнение

Машиночитаемый [результат](../reports/backup_restore/20260929T115202.808221Z/result.json), [backup](../reports/backup_restore/20260929T115202.808221Z/backup.json), [verify](../reports/backup_restore/20260929T115202.808221Z/verify.json), [restore](../reports/backup_restore/20260929T115202.808221Z/restore.json), [лог тестов](../reports/backup_restore/20260929T115202.808221Z/tests.log) и синтетический bundle сохранены локально.

Живой источник имел WAL 135 992 байта при открытом writer. Отдельные CLI-процессы создали и проверили копию, затем восстановили её в новый файл. Размер копии — 49 152 байта, SHA-256 — `b042a9002c4b6bd22a134eb0aa5f0833f59bd22d98eab3378e3ffb39ba739282`. Создание заняло 0,0041 с, восстановление — 0,0028 с внутри утилиты; такие размеры не характеризуют производительность большой рабочей базы.

Прямым чтением восстановленной базы подтверждены точное сохранение `tickets.risk_snapshot`, решения и снимка из `feedback`, отдельной таблицы `snapshots`, произвольной `forecasts` с JSON и бинарными данными. Дополнительная таблица с пробелами и кавычками в имени тоже сохранена.

Девять автоматических тестов прошли:

1. Живая WAL-база, незакоммиченная строка не попадает в копию; весь schema/payload roundtrip совпадает.
2. Другая транзакция коммитит после закрепления снимка; рабочая база содержит новую строку, копия остаётся согласованным прежним снимком.
3. Восстановление поверх существующей открытой базы, повторная запись bundle и dangling symlink отклоняются.
4. Оставшийся WAL выбранного нового имени вызывает отказ, файл WAL не меняется.
5. Несовпадение checksum и не-SQLite файл отклоняются, даже при подмене checksum в manifest.
6. Изменение содержимого решения с пересчитанным checksum файла обнаруживается по сохранённому payload hash.
7. Структурное повреждение страницы при сохранённом SQLite-заголовке и пересчитанном checksum также отклоняется.
8. Искусственный сбой копирования очищает собственный temp и сохраняет посторонний временный файл.
9. Конкурентное создание назначения непосредственно перед rename не приводит к его перезаписи.

Повторение тестов:

```bash
.venv/bin/python -m unittest discover -s tests -p test_database_backup.py -v
```

Контрольные суммы выявляют случайные повреждения и несовпадение с manifest, но не аутентифицируют автора: согласованная злонамеренная подмена одновременно базы и всего manifest не исключается. Копия не зашифрована; каталог создаётся с правами 0700, файлы — 0600. Расписание, retention, отдельное хранилище, disaster recovery, HA, RBAC, произвольная точка восстановления между снимками и проверка всех бизнес-инвариантов не реализованы и не заявляются.
