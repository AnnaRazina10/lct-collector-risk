# Локальный запуск и измерение производительности

Проверено 29 сентября 2026 года. Демонстрационный API возвращает готовые архивные карточки. Отдельный замер ниже действительно вызывает сохранённую объектную LightGBM-модель и восстанавливает её признаки из локальных дневных агрегатов. Производительность чтения JSON не считается скоростью модели.

## Среда и границы проверки

- macOS 15.3.1, arm64, 12 логических CPU, Python 3.12.14; обычный общий компьютер без изоляции от других процессов.
- FastAPI 0.141.1, Uvicorn 0.54.0, Pydantic 2.13.5. Для модели: LightGBM 4.7.0, NumPy 2.5.3, pandas 3.0.6, PyArrow 25.0.1, scikit-learn 1.9.1.
- Полные нагрузочные и ML-замеры выполнены в имеющемся `.venv`, содержащем также исследовательские зависимости. Дополнительно успешно проверена чистая установка `requirements-runtime.txt` на macOS в отдельное окружение без системных site-packages (подробности ниже). Позднее чистая установка `requirements-inference.txt` проверена отдельно: см. раздел ниже и `reports/submission_readiness/clean_inference.json`. В рабочем `.venv` отсутствует модуль `pip`; установка отдельного API-окружения выполнена через `uv`, успешный `pip check` рабочего окружения не заявляется.
- `requirements-runtime.txt` содержит только три прямые зависимости API/UI. `requirements-inference.txt` добавляет зависимости сохранённой объектной модели и её существующего построителя признаков. Версии прямых зависимостей зафиксированы; полный lock с хешами транзитивных зависимостей не создавался.
- Docker CLI 29.8.1 установлен, но daemon недоступен: `/var/run/docker.sock` отсутствует. **Образ не собирался, запуск Linux/container не проверен.** Dockerfile является подготовленным способом запуска, а не результатом успешного развёртывания. Базовый тег `python:3.12-slim` не зафиксирован digest.

## Повторяемые команды

Все команды выполняются из корня репозитория. Исходные данные, модели и `data/app` исключены из Git; одного клонирования недостаточно для воспроизведения демонстрации или ML-замера.

Имеющееся локальное окружение, полный замер:

```bash
.venv/bin/python scripts/verify_runtime.py --users 20 --duration 30 --repeats 100 --ml-threads 2 --connection-mode keep-alive
```

Скрипт выбирает свободный порт на `127.0.0.1`, передаёт уже открытый socket своему единственному процессу Uvicorn, создаёт временную SQLite-базу и выполняет только GET. После проверки завершает и дожидается **только собственного процесса**, удаляет временную БД и закрывает порт. Чужие процессы и пользовательская база не затрагиваются. Если среда ограничивает создание localhost-сокетов, запуск требует разрешения локального сетевого доступа.

Каждый запуск создаёт новый каталог `reports/runtime_validation/<UTC-timestamp>/`: `environment.json`, `summary.json`, `api_requests.csv`, `api_summary.json`, `uvicorn.log`, `inference_samples.csv`, `inference_summary.json`. В режимах `--skip-api` / `--skip-inference` сохраняется соответствующая часть. Выходной код ненулевой при ошибках запросов, изменении исходников/входов во время замера или несовпадении повторных прогнозов.

Дополнительный стрессовый режим новых соединений:

```bash
.venv/bin/python scripts/verify_runtime.py --users 20 --duration 30 --connection-mode new --skip-inference
```

Альтернативная подготовка API-окружения стандартным `venv`/`pip` — именно этот вариант команд не запускался; чистая установка через `uv` проверена ниже:

```bash
python3.12 -m venv /tmp/lct-api-runtime-venv
/tmp/lct-api-runtime-venv/bin/python -m pip install -r requirements-runtime.txt
LCT_TICKET_DB=/tmp/lct-local-tickets.sqlite3 /tmp/lct-api-runtime-venv/bin/python -m uvicorn api.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Для ML-замера вместо этого устанавливается `requirements-inference.txt`; на Linux дополнительно требуется системная библиотека OpenMP для LightGBM. Используется существующая модель, повторного обучения нет. Обязательны:

- `models/object_risk_probe.txt`, `reports/object_risk_probe/configuration.json`;
- `data/interim/daily_2025.parquet`, `data/interim/daily_2026.parquet`;
- `data/raw/справочник_каналов_датчиков.csv`, `data/raw/справочник_объектов_диспетчер.csv`;
- код `src/modeling/object_risk_probe.py` и `src/modeling/export_object_demo.py`.

API требует готовые `data/app/object_risk_demo.json` и, для канального режима, `data/app/risk_demo.json`. Их создание — отдельные скрипты `src/modeling/export_object_demo.py` и `src/modeling/export_risk_demo.py`, которым нужны соответствующие локальные модели, архивные прогнозы и отчёты. Runtime-скрипт эти экспорты не перезаписывает.

Контейнер API/UI после появления доступного Docker daemon:

```bash
docker build -t lct-collector-demo:local .
docker run --rm --name lct-collector-demo -p 127.0.0.1:8040:8000 --mount type=bind,src="$PWD/data/app",dst=/app/data/app,readonly --mount type=volume,src=lct-local-state,dst=/app/state lct-collector-demo:local
```

`.dockerignore` допускает в build context только Dockerfile, runtime requirements, `api/` и `web/`; исходные данные, веса, материалы ТЗ и Git-история в образ не копируются. Архивные карточки подключаются явно и только для чтения, локальные черновики — в отдельном volume. Процесс работает от UID/GID 10001. Образ обслуживает готовые результаты; ML inference в него не включён.

## Методика HTTP

20 потоков изображают 20 одновременно активных читателей. В основном режиме у каждого своё постоянное HTTP/1.1-соединение. После общего стартового барьера каждый без пауз циклически читает шесть маршрутов: health, список объектных рисков, одну объектную карточку, журнал, черновики заявок и историю решений. Фактическое максимальное число запросов в работе проверяется; недостаточно просто задать размер пула 20.

Перед измерением прогреваются все маршруты и создаётся схема пустой временной БД. Проверяется корректный JSON и отсутствие `actual_*`/`outcome` в обычных карточках. Endpoint раскрытия архивного факта не вызывается. Запись заявок и решений не измеряется. GET к журналу/черновикам использует существующий код SQLite, который даже для чтения выполняет проверку/инициализацию схемы; задержки этой реализации входят в результат.

Задержка включает HTTP, чтение тела, разбор JSON и проверки ответа на клиенте. p50/p95/p99 рассчитаны методом nearest rank; сырые значения каждого запроса сохранены. Клиент и сервер работают на одном компьютере. Браузер, отрисовка интерфейса, TLS, корпоративная аутентификация, внешняя сеть, долгий прогон и реальный диспетчерский поток здесь не проверены. Сравнение с одним пользователем не выполнялось, поэтому отсутствие любой деградации относительно одиночного режима не доказано.

## Сохранённые попытки и честные ограничения

1. `20260929T113158.047262Z`: запуск в ограниченной среде остановился на запрете localhost bind. Нагрузки не было; ошибка сохранена в `summary.json`.
2. `20260929T113214.386303Z`: 20 пользователей, новое TCP-соединение на каждый GET. 21 075 запросов за 35,307 с с учётом завершения хвоста, 20 ошибок подключения в конце, p95 93,882 мс, p99 463,208 мс, максимум 7,781 с. Доля ошибок 0,0949%. Причина одновременных connect timeouts не локализована; ограничение частого создания локальных соединений — гипотеза, не установленный диагноз. ML-часть этой серии прошла отдельно.
3. `20260929T113333.753483Z`: постоянные соединения, 25 636 запросов, 0 ошибок. Во время замера другой агент завершил исправление API, и проверка контрольной суммы правильно отметила `source_files_unchanged=false`. Серия сохранена, но не считается проверкой окончательной неизменной версии. ML-часть прошла и от изменения API не зависит.

Неуспешные серии не удалены и не заменены успешным отчётом. Итоговый замер окончательной версии приведён ниже.
