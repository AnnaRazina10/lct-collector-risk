# Стратегия решения

## Победная ставка

Не пытаться одинаково глубоко закрыть все направления кейса. Для MVP выбрать
направление "Отказ датчика" и снижение ложных тревог, а остальные направления
показать как расширяемые сценарии той же платформы.

Такой фокус дает три преимущества:

- задача лучше всего поддержана доступными событиями датчиков;
- можно честно посчитать precision/recall на временной тестовой выборке;
- продуктовая польза понятна заказчику: меньше ложных выездов, понятнее приоритеты,
  быстрее формирование профилактических заявок.

## ML-постановка

Основная задача: для каждого канала датчика или объекта в момент времени `t` оценить
вероятность проблемного состояния в следующие 24 часа.

Возможные варианты целевой переменной:

1. `sensor_alarm_next_24h` - будет ли тревожное событие по каналу в следующие 24 часа.
2. `sensor_noise_cluster_next_24h` - появится ли кластер частых тревог или резких
   переключений, похожий на деградацию датчика.
3. `object_risk_next_24h` - появится ли проблемный паттерн хотя бы по одному каналу
   объекта в следующие 24 часа.

Для первого baseline рекомендуется начать с `sensor_alarm_next_24h`, затем уточнить
разметку через правила ложных срабатываний и серийности.

## Фичи

Фичи по каналу датчика:

- количество событий за 5 минут, 1 час, 6 часов, 24 часа, 7 дней;
- количество и доля тревожных событий за те же окна;
- время с последнего события;
- время с последнего тревожного события;
- длина текущей серии одинаковых значений;
- число переключений состояния;
- среднее, минимум, максимум, стандартное отклонение значения датчика;
- скачки значения и отклонение от обычного уровня канала.

Фичи по объекту:

- число активных каналов;
- число тревожных каналов;
- доля тревожных каналов;
- агрегаты по типам датчиков;
- интенсивность событий по объекту.

Категориальные и календарные фичи:

- тип инженерной системы;
- тип датчика;
- идентификатор объекта;
- уровень объекта в иерархии;
- час суток;
- день недели;
- месяц;
- признак выходного/рабочего дня, если календарь будет добавлен.

## Модели

Baseline:

- эвристический скоринг по частоте тревог и аномальной активности;
- Logistic Regression или Random Forest для быстрой проверки постановки;
- CatBoost или LightGBM как основной табличный baseline.

Основная модель:

- CatBoostClassifier или LightGBMClassifier;
- class weights или sampling для дисбаланса;
- калибровка вероятностей;
- подбор порога под требование Precision > 0.7 при максимальном Recall.

Объяснимость:

- топ признаков по модели;
- SHAP/feature contribution для аналитиков;
- человекочитаемые причины в интерфейсе: "частота тревог выросла", "датчик часто
  переключается", "значение вышло из типичного диапазона".

## Валидация

Использовать только временное разбиение:

- train: ранние годы;
- validation: следующий временной период;
- test: последний доступный период.

Нельзя использовать случайный split по строкам, потому что он создаст утечки между
соседними событиями одного датчика.

Метрики:

- Precision;
- Recall;
- F1;
- PR-AUC;
- top-K precision для диспетчерской очереди;
- latency inference;
- количество предотвращенных или отфильтрованных ложных тревог в симуляции.

## Продуктовый сценарий

1. Поток событий поступает из СМВУ или проигрывается из исторического журнала.
2. Feature pipeline пересчитывает агрегаты.
3. Model service формирует риск на горизонте 24 часа.
4. Dashboard показывает диспетчеру очередь рисков.
5. Диспетчер открывает карточку риска и видит объяснение.
6. Система предлагает действие: проверить датчик, наблюдать, сформировать заявку.
7. Результат решения сохраняется как feedback для анализа и дообучения.

## Архитектура MVP

```text
CSV/7z -> ingestion -> parquet/features -> model -> FastAPI -> dashboard
                                      -> PostgreSQL -> журнал прогнозов
```

Компоненты:

- `src/` - обработка данных, генерация фичей, обучение моделей;
- `api/` - REST API для прогнозов, рисков, объектов, заявок и feedback;
- `web/` - дашборд диспетчера;
- `notebooks/` - EDA и эксперименты.

## Что показать на питче

Главный тезис: сервис не заменяет диспетчера, а превращает поток тревог в
приоритизированную очередь действий.

Демо:

1. Исторический день проигрывается как поток.
2. Система выделяет топ рискованных датчиков/объектов.
3. В карточке риска показаны вероятность, горизонт и причины.
4. Диспетчер формирует черновик заявки.
5. Журнал сохраняет прогноз, решение и статус.
6. Отдельно показываются метрики модели и скорость расчета.

## Риски

- Сильный дисбаланс классов.
- Неполная разметка истинных отказов и ложных тревог.
- Возможные различия между архивными данными и боевым потоком.
- Необходимость аккуратно разделять прогноз инцидента и детекцию уже произошедшего
  события.

## Приоритеты разработки

1. EDA и витрина данных.
2. Формализация target на 24 часа.
3. Baseline-модель и временная валидация.
4. API для прогнозов и очереди рисков.
5. Диспетчерский dashboard.
6. Симулятор исторического потока для демо.
7. Документация, презентация и инструкция запуска.
