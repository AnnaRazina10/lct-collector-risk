# Оставшиеся приоритеты и контракт локальных рекомендаций

Исходная проверка выполнена 29.09.2026 по коду `050384c` и оригиналу [ТЗ 2026](<materials/8. ДЖКХ.pdf>); ниже учтены последующие изменения. Три локальных этапа — рекомендации, foreground-backup и сопоставимая нагрузка — выполнены в описанном объёме. Прошли [170 Python-тестов](../reports/runtime_comparison/full_tests.log), [семь сценариев Node](../reports/recommendations/web_async_check.json), [1 981 независимая проверка рекомендаций](../reports/recommendations/independent_review.json) и [40 проверок автоматического backup](../reports/automatic_backup/independent_review.json). Отдельно подтверждено [реальное браузерное сохранение и перезапуск сервера](../reports/recommendations/http_restart.json). Промышленные ограничения остаются. Требования приведены в [requirements.md](requirements.md), состояние рекомендаций — в [recommendations.md](recommendations.md), общая готовность — в [readiness_audit.md](readiness_audit.md).

## Основание приоритетов

В [§§17–18, страницы PDF 13–14](<materials/8. ДЖКХ.pdf#page=13>) нет численных весов или балльной шкалы. Экспертиза явно учитывает проверку расчётов, сопоставление прогноза с реальными значениями, качество рекомендаций при текущих вводных, интеграцию, скорость, удобство, дополнительные настраиваемые параметры и объективность диаграмм. Порядок ниже — инженерная оценка полезности за ограниченное время, а не официальные веса жюри.

Общие рекомендации по обслуживанию входят в [§6](<materials/8. ДЖКХ.pdf#page=8>). Расширенная аналитика, модуль дообучения, черновики заявок и дополнительные отчёты перечислены в [§8](<materials/8. ДЖКХ.pdf#page=8>) с оговоркой «по согласованию с Заказчиком». Наличие черновика само по себе не доказывает качество ремонтных рекомендаций.

Исходная оценка пунктов 1–3 составляла 135–195 минут. Все три локальных этапа теперь имеют код и проверочные свидетельства; прежние оценки не являются оставшейся работой или гарантированным SLA. [Независимый review хранения](../reports/runtime_comparison/storage_review.md) подтверждает сохранение проверок целостности и отсутствие существенных регрессий в рассмотренном изменении. Комплект v2 предшествует backup/storage-изменениям; новый v3 только планируется после фиксации кода.

Альтернативный расход всего бюджета — локальная аутентификация, роли viewer/dispatcher/admin и журнал разрешённых/отклонённых действий. В текущем API `operator` приходит от клиента, личность не подтверждается. Реализация приблизит требования [§11](<materials/8. ДЖКХ.pdf#page=10>), но потребует согласованных изменений API, UI, тестов и запуска комплекта; LDAP/AD локальными учётными записями не подтверждается. Перед сдачей риск регрессий выше, чем у независимого модуля рекомендаций.

Уверенность в расхождениях с ТЗ высокая; оценки трудоёмкости и приоритетов — средняя. Новые статьи, декоративные интеграции и повторная упаковка не входят в этот бюджет.

## Контракт отдельного модуля рекомендаций

Реализованный модуль [local_recommendations.py](../src/serving/local_recommendations.py) содержит чистую функцию `recommend(facts: Mapping[str, object], context: Mapping[str, object]) -> dict`. Он не читает файлы, базу, сеть, системное время или пользовательские сообщения, не обучает модель и не вызывает API. Рекомендация является предложением диспетчеру проверить информацию, а не инструкцией управлять оборудованием или выполнять ремонт. Версия схемы — `1.0`, правил — `1.0.0`; `RULESET_SHA256` вычисляется по спецификации правил, текстам и версии, а не является хешем всего исходного файла.

Слово «каузальный» здесь означает только отсутствие сведений из будущего относительно выпуска. Доступные корреляции и журнальные записи не устанавливают физическую причину события.

### Вход и граница времени

Адаптер извлекает вход из проверенной сервером архивной карточки и её выпуска; значения из клиентского тела запроса не являются источником фактов. Модуль не получает целый payload, `explanation`, исходы, feedback или произвольный текст.

| Поле | Контракт |
|---|---|
| `context.run_id`, `card_id`, `object_id` | Точные непустые идентификаторы одного сохранённого выпуска/карточки. Модуль проверяет `card_id == run_id + '_' + object_id` и префикс `object_`/`onset_` по цели; существование и подлинность выпуска проверяет адаптер |
| `context.goal` | Явное нормализованное значение `any_alarm` или `registered_episode_start_g1`. У старых any-alarm выпусков `target_kind` может отсутствовать; адаптер нормализует его в `any_alarm`. Отображаемое название цели не используется |
| `context.mode` | Только `historical_replay` в первой версии; отсутствие live-подключения сохраняется в результате |
| `feature_date`, `feature_cutoff`, `issue_time`, `forecast_start`, `forecast_end` | Обязательный дневной контракт v1: cutoff D 23:59:59 MSK, issue D+1 00:00, target D+2 00:00…D+3 00:00; ровно 24 часа до начала окна. Эквивалентные UTC timestamps допустимы и нормализуются в MSK. Другие окна/отсутствие timezone отклоняются. Проверка provenance и доступности пакетов/модели остаётся обязанностью существующего producer; даты карточки сами по себе её не доказывают |
| `observed_channels`, `catalog_channels`, `events_today`, `alarm_channels` | Неотрицательные целые счётчики из текущей карточки |
| `current_alarm`, `warning` | Булевы значения из карточки; первое означает наличие тревожной записи в день признаков, второе — уже принятое модельной политикой решение очереди |
| `alarm_days_7d`, `observed_days_7d` | Целые 0…7; окно заканчивается днём признаков. Отсутствие записи не означает подтверждённое отсутствие неисправности |
| `rank` | Необязательное целое поле для onset, только отображение уже сохранённого места; не пересчитывается |

`score` не нужен правилам: его пороги не подбираются, вероятность из него не выводится. Значения `fault`, `no_power`, тип датчика и координаты в текущих объектных карточках отсутствуют; первая версия не добавляет предположений о них. Никакие сведения за D+1/D+2 и поля `actual_*`, `outcome`, `records_intermediate`, `records_target`, `onset_target` не допускаются. Неизвестные входные поля следует отклонять, а не анализировать.

Неизвестные поля, неверные идентификаторы или временной контекст вызывают `RecommendationValidationError`, подкласс `ValueError`. Отсутствующие, неверно типизированные или противоречивые обязательные факты дают `status=insufficient_data`, `validation_errors` и пустые `steps`/`evidence`, без предметной рекомендации. Примеры противоречий: отрицательные счётчики; `current_alarm=true` при нуле тревоживших каналов; тревоживших каналов больше, чем каналов с записями; тревожных дней больше, чем дней с записями. Число наблюдаемых каналов выше справочного даёт тот же статус недостаточных данных, а не диагноз или исправление справочника. Искусственного верхнего лимита числа записей за день нет. API перехватывает ошибку контекста как `status=unavailable`; UI показывает недоступность рекомендации отдельно, сохраняя исходную карточку.

### Детерминированные правила и текст

Правила применяются в фиксированном порядке. Допустимы несколько независимых оснований, не более трёх шагов проверки. Значение «два дня» ниже — прозрачное правило интерфейса, не результат подбора качества по тесту.

| Условие по известным фактам | Код правила | Предлагаемый текст |
|---|---|---|
| `observed_channels == 0` | `NO_RECORDS_TODAY` | «За день признаков записи не зарегистрированы. Проверьте доступность источника данных и журнал поступления. По отсутствию записей состояние оборудования не установлено». Приоритет над остальными правилами; остальные факты можно показывать справочно |
| `0 < observed_channels < catalog_channels` | `PARTIAL_CATALOG_RECORDS` | «Записи есть по X из Y справочных каналов. Уточните ожидаемый режим регистрации и полноту поступления; отсутствие записей по каналу не доказывает неисправность» |
| `current_alarm == true` | `ALARM_RECORDED_TODAY` | «В день признаков уже были тревожные записи. Сопоставьте их с журналом диспетчера и ранее принятыми решениями; необходимость осмотра определяет диспетчер» |
| `alarm_days_7d >= 2` | `MULTIPLE_ALARM_DAYS` | «За последние семь календарных дней тревожные записи отмечены в N днях. Проверьте их повторяемость и предыдущую отработку по журналу». Не называть N дней числом отдельных аварий или непрерывной серией |
| Ни одно правило выше не применимо; `warning == true` | `SELECTED_FOR_REVIEW` | «Объект включён в очередь проверки. Сопоставьте доступные наблюдения и журнал диспетчера; модельная оценка сама по себе не подтверждает поломку» |
| Ни одно правило выше не применимо; `warning == false` | `OUTSIDE_WARNING_POLICY` | «Объект не выбран действующей политикой предупреждений. Отсутствие предупреждения не подтверждает исправность; дополнительных оснований для рекомендации в переданных фактах нет» |

Текущая тревога не исключает объект из onset-очереди: D+1 неизвестен при выпуске. Модуль не фильтрует карточки, не подавляет повторные предупреждения, не меняет top-10, tie-break, ранги, пороги и score. Он также не заявляет о прочтении журналов или плановых работ — только предлагает диспетчеру их сопоставить.

### Результат и журнал

Результат содержит `schema_version`, `ruleset_version`, `ruleset_sha256`, `status`, нормализованный контекст, `fact_cutoff`, `recommendation_id`, упорядоченный `rule_ids`, список `evidence`, `validation_errors` и `steps` вида `{rule_id, text, evidence_fields}`. Для наблюдений evidence имеет `{field, value, source: 'observation', window_end: feature_cutoff}`. Поля `warning`/`rank` являются результатами политики при выпуске: `{field, value, source: 'forecast_policy', available_at: issue_time}`, без `window_end`. Они не выдаются за наблюдения дня D. Отдельно: `requires_dispatcher_decision=true`, `external_send=false`, ограничение исторического replay и отсутствия доказанной физической причины.

`recommendation_id` детерминирован: SHA-256 от канонического JSON идентификаторов, цели, версии правил и всех разрешённых фактов. Фактическое `generated_at` добавляет вызывающий слой; оно не подменяет историческое время доступности модели/данных и не входит в детерминированный идентификатор. Тексты и версии правил входят в хеш набора правил.

API хранит рекомендацию отдельным снимком рядом с новым локальным решением/черновиком, включая правила и использованные факты. Существующие forecast payload, их хеши и записи не перезаписываются. Исторически сгенерированная сегодня рекомендация маркируется как сегодняшняя обработка архивных данных; нельзя утверждать, что соответствующее правило уже использовалось в историческую дату. Сохранение решения происходит только по явному действию пользователя; автоматических заявок, отправок, назначения ремонта или смены статусов нет. Повторный черновик сохраняет первоначальный снимок; чтение журнала не пересчитывает старые рекомендации. Поддельные клиентские факты и тексты рекомендаций не становятся источником снимка.

### Подтверждённые проверки и оставшиеся ограничения

- Чистый модуль: [22 теста](../tests/test_local_recommendations.py) проверяют шесть правил, порядок, пропуски, противоречия, будущие поля, временные границы, типы и детерминированность. Две запасные ветви очереди покрыты синтетически; в 468 реальных карточках они не сработали.
- Интеграция рекомендаций первоначально прошла [151 Python-тест](../reports/recommendations/integration_tests.log); текущий общий прогон после backup/storage-изменений — [170 тестов](../reports/runtime_comparison/full_tests.log). [Семь сценариев Node](../reports/recommendations/web_async_check.json) проверяют асинхронный UI на минимальном DOM, без реального браузера/сети/БД.
- Независимая проверка: [6 выпусков / 468 карточек / 1 981 проверка](../reports/recommendations/independent_review.md), все `status=ok`. Сохранены исходные payload, content hashes, score, warning, rank и top-10 каждого onset-выпуска. Правила не выбирались по исходам 2026.
- В отдельной временной SQLite через TestClient проверены серверный снимок feedback/ticket, защита от подмены клиентских фактов, повторный черновик и чтение прежнего снимка новым клиентом после замены функции рекомендаций. Рабочие решения не читались и не менялись. Повторное создание TestClient не считается реальным рестартом процесса.
- В [отдельной браузерной/restart-проверке](../reports/recommendations/http_restart.json) на тестовой `recommendation_demo.sqlite3` явно сохранено одно решение и показана его рекомендация. После остановки сервера и старта нового процесса журнал и метаданные шести выпусков по HTTP полностью совпали. Ошибок браузерной консоли — 0; внешней отправки и использования рабочей БД не было. Скриншоты [сохранения](../reports/recommendations/ui_verified.png) и [журнала](../reports/recommendations/ui_journal_verified.png) просмотрены. Остальные браузеры, реальные пользователи и промышленная инфраструктура этим сценарием не проверены.
- Различающиеся шаги проверки подтверждены; эффективность в предотвращении отказов, корректность ремонта и экономический эффект не проверены. Полное выполнение §6/§18 не заявляется.

Актуальное описание HTTP-контракта и границ проверки — [recommendations.md](recommendations.md). Реализация рекомендаций добавляет отдельный результат к API/UI и снимкам решений; модели и исходные прогнозы не изменяет. Проверенные исходники и их SHA перечислены в независимом отчёте.
