# Автоматические локальные копии SQLite

[backup_scheduler.py](../scripts/backup_scheduler.py) запускает проверенное [SQLite online backup](backup_restore.md) сразу и затем по заданному интервалу. Исполнитель работает только после явного запуска команды. Он не устанавливает cron, системную службу или задачу приложения, не меняет API/UI и не удаляет прежние копии.

Локальная проверка на macOS завершена: [15 тестов](../tests/test_backup_scheduler.py) и [40 независимых проверок](../reports/automatic_backup/independent_review.json) прошли. Независимый прогон использовал отдельную временную копию базы из review-v2: шесть выпусков, 468 карточек и отдельно созданное сервером тестовое решение со снимком рекомендации. Рабочие пользовательские БД не открывались.

## Запуск

```bash
.venv/bin/python scripts/backup_scheduler.py \
  --source /absolute/path/to/authorized-test.sqlite3 \
  --output-dir /absolute/path/to/separate-backup-directory \
  --interval 3600 \
  --timeout 60 \
  --max-runs 3
```

| Аргумент | Значение |
|---|---|
| `--source` | Обязательный путь к разрешённой SQLite-базе. Исполнитель не создаёт отсутствующую базу; ошибка фиксируется, следующая попытка выполняется по расписанию |
| `--output-dir` | Обязательный отдельный каталог копий, привязанный к одному источнику. Источник не может находиться внутри него. Каталог создаётся при необходимости |
| `--interval` | Секунды между слотами расписания, по умолчанию 3600. Конечное число от 0,01 до 31 536 000 |
| `--timeout` | Кооперативный лимит одной операции backup, по умолчанию 60 секунд; конечное число строго больше 0 и не больше 86 400 |
| `--max-runs` | Положительное целое число **попыток** за текущий запуск, включая неудачные. Без аргумента процесс работает до сигнала остановки |

Нулевая, отрицательная, бесконечная или NaN-настройка отклоняется до создания каталога вывода. Нижний предел интервала исключает бессмысленное расписание полных проверенных копий чаще одного раза в 10 мс. В рабочих локальных запусках интервал следует выбирать по размеру базы и измеренной длительности копирования.

Первую попытку исполнитель начинает сразу, в том числе после перезапуска. Дальнейшие слоты вычисляются по `time.monotonic()`. Если копирование заняло несколько интервалов, пропущенные слоты учитываются в `skipped_slots`, следующая попытка назначается на первый будущий слот. Серия догоняющих запусков не выполняется. UTC-время в статусе служит для чтения человеком, а не для управления расписанием.

Для безопасного воспроизводимого примера можно создать новую синтетическую базу в уникальном временном каталоге:

```bash
backup_demo_dir="$(mktemp -d /private/tmp/lct-backup-demo.XXXXXX)"
.venv/bin/python - "$backup_demo_dir/source.sqlite3" <<'PY'
import sqlite3
import sys
with sqlite3.connect(sys.argv[1]) as db:
    db.execute("CREATE TABLE test_snapshots(id INTEGER PRIMARY KEY, payload TEXT)")
    db.execute("INSERT INTO test_snapshots VALUES (1, ?)", ("ТЕСТ: локальная копия",))
PY
.venv/bin/python scripts/backup_scheduler.py \
  --source "$backup_demo_dir/source.sqlite3" \
  --output-dir "$backup_demo_dir/copies" \
  --interval 1 --timeout 10 --max-runs 3
```

Пример не использует рабочую базу. Копии и статус остаются в созданном каталоге; автоматического удаления нет.

## Защита от параллельного запуска и перезаписи

Один процесс владеет каталогом через неблокирующий эксклюзивный `flock` файла `.backup_scheduler.lock`. PID записан в статусе только для справки и не служит механизмом блокировки. Дескриптор закрывается при обычном завершении; ОС снимает блокировку также после SIGKILL. Сам lock-файл намеренно остаётся: удаление файла могло бы позволить двум процессам блокировать разные inode.

Пути разрешаются до абсолютных, поэтому обращение к тому же каталогу через символьную ссылку не создаёт отдельного расписания. Lock/status не открываются через конечную символьную ссылку. Блокировка кооперативная, предназначена для локального каталога: она не защищает от сторонней программы, которая намеренно удаляет или заменяет lock-файл.

Каждая попытка получает уникальный каталог `backup-<UTC>-<UUID>`. Публикация выполняется существующим backup-кодом с запретом перезаписи, после проверки SQLite, схемы, числа строк, содержимого и checksum manifest. Исполнитель не перезаписывает и не удаляет опубликованные копии. При ошибке исходный backup-код очищает только свой временный каталог.

Повторный запуск в том же output-dir сохраняет накопленные счётчики и историю успеха/ошибки. Несовместимый, повреждённый status или другой `source` приводят к отказу без замены прежнего статуса. Для другого источника используется другой output-dir.

## Статус и обработка ошибок

`output-dir/status.json` заменяется атомарно через временный файл, `fsync` и `os.replace`. Читатель видит целый старый или новый JSON. Перезапись относится только к status, не к копиям. При невозможности сохранить статус исполнитель прекращает работу и сообщает ошибку в stderr: продолжение с неучтёнными копиями не выполняется.

| Поле | Смысл |
|---|---|
| `format_version` | Версия структуры, сейчас 1 |
| `source`, `output_dir` | Нормализованные абсолютные пути |
| `session_id`, `pid`, `started_at_utc`, `updated_at_utc` | Текущий запуск и время последнего сохранения статуса |
| `state` | `starting`, `backing_up`, `waiting` или `stopped` |
| `interval_seconds`, `timeout_seconds`, `max_runs` | Настройки текущего запуска |
| `session_attempts`, `session_successes`, `session_failures` | Счётчики только текущего запуска |
| `counters` | Накопленные `attempts`, `successes`, `failures`, `interrupted`, сохраняемые между запусками |
| `skipped_slots` | Пропущенные слоты расписания текущего запуска |
| `last_attempt` | `attempt_id`, `destination`, `status`, начало/конец в UTC; при ошибке также `error`. Статусы: `in_progress`, `succeeded`, `failed`, `interrupted` |
| `last_success` | Последняя подтверждённая успешная копия: `destination`, `completed_at_utc`, SHA базы и manifest, длительность, режим журнала источника |
| `last_error` | Последняя историческая ошибка: тип, сообщение, время и attempt ID. После следующего успеха она не стирается |
| `next_attempt_at_utc` | Оценка времени следующей попытки для человека; вне ожидания — null |
| `stopped_at_utc`, `stop_reason` | Завершение и причина: `max_runs`, `requested` либо `signal:SIGTERM` / `signal:SIGINT` |

Ошибка копирования увеличивает счётчик failures, сохраняет подробности и **не уничтожает `last_success`**. После ошибки следующая попытка идёт по расписанию. Для понимания текущего результата нужно смотреть `last_attempt.status`; непустой `last_error` после recovery не означает, что последняя попытка тоже неуспешна.

После аварийного завершения статус может остаться `in_progress`. Следующий запуск под lock отмечает предыдущую попытку как `interrupted`, сохраняет прежний успех и начинает новую попытку. Копия, успевшая опубликоваться до потери процесса/статуса, не удаляется и автоматически не объявляется успешной: её можно проверить по manifest. После SIGKILL также могут остаться временные файлы; исполнитель не удаляет неизвестные остатки прежних запусков.

## Остановка и коды завершения

SIGTERM и SIGINT прерывают ожидание и запрещают следующую попытку. Если операция уже началась, ей дают закончить проверку/публикацию или штатно вернуть ошибку, затем сохраняется конечный статус и освобождается lock. Лимит исходного backup-кода кооперативный: отдельное SQLite-ожидание или системный вызов может завершиться позже указанного timeout. Мгновенное прекращение активной копии и жёсткий real-time deadline не обещаются.

| Код | Значение |
|---|---|
| 0 | Ограниченный запуск закончился без ошибок копирования в этой сессии |
| 1 | Ошибка исполнения/статуса либо в сессии была хотя бы одна неудачная попытка, даже если затем произошло восстановление |
| 2 | Ошибка аргументов CLI |
| 3 | Другой процесс уже владеет flock данного output-dir; его status не изменён |
| 130 / 143 | Штатная обработка SIGINT / SIGTERM, соответственно |

## Проверка и восстановление

Последний подтверждённый путь находится в `last_success.destination`. Для проверки и восстановления используются существующие команды; destination восстановления должен быть **новым**:

```bash
.venv/bin/python scripts/database_backup.py verify \
  --bundle /absolute/path/from-last-success
.venv/bin/python scripts/database_backup.py restore \
  --bundle /absolute/path/from-last-success \
  --destination /absolute/path/to/new-restored.sqlite3
```

После отдельной проверки API можно запустить на восстановленной базе через `LCT_TICKET_DB`; процедура и запрет перезаписи описаны в [backup_restore.md](backup_restore.md). Исполнитель не переключает действующий API и не выполняет автоматическое восстановление.

Проверки этой реализации:

- [15 тестов](../tests/test_backup_scheduler.py): реальные конкурирующие subprocess, освобождение flock после SIGKILL, SIGINT в ожидании, SIGTERM во время копии, исчезновение/возвращение источника, сохранение прежнего успеха, восстановление payload, live WAL с незакоммиченной записью, уникальность копий, неверные параметры, повреждённый status и ошибка атомарной записи. Команда: `.venv/bin/python -m unittest discover -s tests -p 'test_backup_scheduler.py' -v`.
- [Независимый black-box прогон](../reports/automatic_backup/independent_review.json): 40 проверок за 2,40 секунды; три периодические копии, конфликт flock, пропущенные слоты после реального SQLite exclusive lock, ошибка отсутствующего источника и recovery, остановка/перезапуск и точное восстановление шести выпусков, 468 карточек и тестового снимка рекомендации. За 125 чтений status не встретился частичный JSON. Измеренное восстановление небольшой тестовой базы — около 0,010 секунды; показатель не переносится на произвольный объём данных.

## Эксплуатационные ограничения

Подтверждён локальный macOS-прогон. Linux-ветка существующей атомарной публикации, Linux/container и Windows не проверены; Windows flock не поддерживается. Проверка не подтверждает PostgreSQL, LDAP/AD, HA, внешнее хранилище, шифрование копий, retention, автозапуск после загрузки ОС или полное выполнение §11 ТЗ.

Копируется main SQLite-база, включая выпуски, решения и сохранённые в их снимках рекомендации, но не внешние JSON, модели и присоединённые БД. Рекомендация вложена в `risk_snapshot` таблиц `feedback`/`tickets`; отдельная таблица рекомендаций не требуется. Копии не шифруются; manifest выявляет повреждения, но не аутентифицирует автора. База и копии на одном устройстве подвержены общему отказу носителя. Длительный запуск без `max-runs` расходует дисковое место, поскольку удаление старых копий намеренно отсутствует. Без данных о реальном объёме, носителе и регламенте заказчика SLA восстановления ≤4 часов, RPO и промышленная готовность не заявляются.
