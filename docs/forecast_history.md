# Неизменяемый архив выпусков и выбор расчёта

Объектный интерфейс умеет выбирать сохранённый выпуск исторического расчёта. Старые автономные объектная и канальная демонстрации продолжают работать без `run_id`. Новые выпуски не содержат будущих исходов: интерфейс не показывает кнопку их раскрытия, API возвращает 404 и не обращается к старому архиву за фактом.

`issue_time` обозначает историческое время, в которое прогноз мог бы быть выпущен при указанном отсечении данных. `created_at` в метаданных — фактическое время сохранения расчёта сейчас. Режим называется `historical_replay`; он не означает подключённый поток текущих наблюдений. На карточках нового выпуска показаны его собственные даты, число объектов, предупреждения и горизонт. Метрики прошлого эксперимента не выдаются за оценку качества выбранного выпуска.

## Контракт публикации

Независимый модуль `api/forecast_store.py` не импортирует FastAPI, обучение, модели или архив фактических исходов. Producer вызывает:

```python
from pathlib import Path
from api.forecast_store import publish_run, load_run, list_runs, get_run_metadata

metadata = publish_run(Path("data/app/forecast_replay.sqlite3"), payload)
stored_payload = load_run(Path("data/app/forecast_replay.sqlite3"), metadata["run_id"], entity_mode="object")
```

Обязательные поля `payload`:

| Поле | Условие |
| --- | --- |
| `run_id` | 1–160 символов из `A–Z a–z 0–9 _ . : -` |
| `entity_mode` | `object` |
| `mode` | `historical_replay` |
| `feature_date` | Строго `YYYY-MM-DD` |
| `feature_cutoff` | ISO timestamp с часовым поясом, дата по МСК равна `feature_date`, раньше выпуска |
| `issue_time` | ISO timestamp с часовым поясом, не раньше окончания дня признаков по МСК |
| `forecast_start`, `forecast_end` | ISO timestamps с часовым поясом; конец позже начала |
| `minimum_lead_hours` | Конечное число, точно соответствует `forecast_start − issue_time`, не меньше 24 часов |
| `model_sha256`, `input_sha256` | SHA-256 в виде 64 шестнадцатеричных символов |
| `threshold` | Конечное число в диапазоне [0, 1] |
| `cards` | Непустой список карточек |

У карточки обязательны уникальный `id` длиной до 256 символов, содержащий `run_id`, числовой конечный `score` в [0, 1] и булев `warning`, совпадающий с `score >= threshold`. Если переданы `object_id`, они не повторяются внутри выпуска; если передан `entity_mode`, он равен `object`. Идентификатор карточки нельзя повторно использовать в другом выпуске. Поля `total_objects`, `shown_cards`, `warnings_count`, `window_hours`, если присутствуют, проверяются на соответствие содержимому.

На любой глубине JSON запрещены `actual_*`, `actual`, `outcome`, `outcomes`, `target_any_object_alarm_d_plus_2`, включая регистр написания. `NaN`, бесконечность и значения, не представимые обычным JSON, отклоняются. Календарные сведения и описание целевой задачи допускаются, наблюдённые будущие исходы — нет. Хранилище проверяет договорённость о времени, но не заменяет причинную проверку вычисления признаков producer-ом.

Дополнительные поля карточек для интерфейса — название объекта, группа, наличие записей, агрегаты тревог, объяснение и рекомендация — сохраняются вместе с выпуском. Схема групп не считается реальной географической картой.

## Неизменяемость и целостность

Публикация выполняется одной транзакцией SQLite. JSON канонизируется с сортировкой ключей и фиксированными разделителями; SHA-256 вычисляется по UTF-8 байтам. Повтор одного `run_id` с тем же каноническим содержимым возвращает прежние метаданные и первоначальный `created_at`. Изменённое содержимое под тем же идентификатором вызывает `ForecastConflictError`; новый выпуск требует нового идентификатора.

Таблицы `forecast_runs` и `forecast_card_ids` защищены триггерами от SQL UPDATE и DELETE. Резервирование идентификаторов карточек атомарно с публикацией: конфликт откатывает весь новый выпуск. Одновременные одинаковые повторы не создают дубликаты.

`load_run`, `get_run_metadata` и `list_runs` открывают БД только для чтения, проверяют хеш, каноническую форму, схему, отсутствие будущих исходов и согласованность метаданных с payload. Повреждение вызывает `ForecastIntegrityError`, API отвечает 503; подмена недоступного выпуска старой демонстрацией не выполняется. Неизвестный `run_id` и несовпадение режима вызывают `ForecastNotFoundError` / HTTP 404. Пустая или прежняя БД без таблиц выпусков даёт пустой список без создания таблиц при чтении.

Механизм защищает историю от обычных изменений приложения и обнаруживает несогласованность данных. Он не является электронной подписью или защитой от владельца компьютера, который может отключить триггеры и переписать БД вместе с хешами. Для производственного аудита нужны управление доступом, доверенное журналирование, резервные копии и организационные правила хранения.

## API и интерфейс

Все выпуски, черновики и решения используют общую БД из `LCT_TICKET_DB`; значение по умолчанию — `data/app/tickets.sqlite3`. Для сформированного архива:

```bash
LCT_TICKET_DB=data/app/forecast_replay.sqlite3 .venv/bin/python -m uvicorn api.main:app --host 127.0.0.1 --port 8765
```

| Запрос | Результат |
| --- | --- |
| `GET /api/forecast-runs?mode=object&limit=100` | Метаданные выпусков, новые исторические даты сначала; максимум 500 |
| `GET /api/risks?mode=object&run_id=…` | Карточки конкретного выпуска и `archive_metadata` |
| `GET /api/risks/{id}?mode=object&run_id=…` | Снимок карточки выбранного выпуска |
| `GET /api/risks/{id}/outcome?mode=object&run_id=…` | 404: исходы нового выпуска не хранятся |
| `POST /api/tickets` | В теле передаются `risk_id`, `entity_mode`, `run_id`, `note` |
| `POST /api/feedback` | Тот же `run_id` плюс решение, основание, имя диспетчера и комментарий |

Метаданные включают `run_id`, режим, времена, горизонт, модель/входные хеши, порог, `cards_count`, `content_sha256`, `created_at`. Оригинальный payload не изменяется: `archive_metadata` добавляет только API при выдаче. Без `run_id` действуют прежние маршруты; режим API по умолчанию остаётся `channel`.

В объектном режиме появился выбор между исходной архивной демонстрацией и отдельной группой сохранённых исторических расчётов. Выбор отражается в URL. Метаданные фактического сохранения и исторического выпуска показаны раздельно. При сохранении черновика или решения фиксируются `run_id`, даты, модель, хешы, порог, оценка и карточка именно выбранного выпуска. Позднее переключение интерфейса не меняет уже сохранённый снимок.

Локальный журнал показывает последние 200 решений/черновиков всех выпусков выбранного режима и подписывает выпуск каждой записи. Checkbox «Все режимы» расширяет журнал также на канальные записи. Старая история без `run_id` явно обозначена как исходная архивная демонстрация. Решения сохраняются как отдельные записи; редактирование или удаление прошлой обратной связи через API не предоставлено. Имя диспетчера по-прежнему вводится локально, без проверки корпоративной идентичности.

## Подтверждённые проверки и ограничения

13 новых регрессионных тестов в `tests/test_forecast_store.py` и `tests/test_api_forecasts.py` прошли. Проверены канонический идемпотентный повтор, конкурентная публикация, откат конфликтов, запрет UPDATE/DELETE, повреждение содержимого, вложенные будущие исходы, нечисловые и бесконечные оценки, временные ограничения, неизвестный выпуск, изоляция режима, сохранение разных выпусков в снимках решений и совместимость старых маршрутов. Прежние 8 API-тестов также прошли после изменений.

Реальные выпуски на данных за 26, 27 и 28 июня 2026 приняты тем же строгим хранилищем: по 78 карточек, всего 234. Воспроизведение producer-а и проверки поздних пакетов находятся в `reports/forecast_replay/verification.json`; интеграционные проверки и проверка перезапуска — в том же каталоге. Новый хранилищный и API-код не обучает модель и не меняет порог.

Остаются ограничения: исторический replay не является непрерывным сервисом сбора данных; метка описывает зарегистрированную тревогу, а не доказанную физическую неисправность; вероятность не откалибрована; корпоративная авторизация, реальная карта, внешняя система заявок и производственное защищённое развёртывание не подключены. SQLite-архив должен входить в резервное копирование вместе с локальным журналом. Все операционные утверждения требуют отдельной проверки на подключённой инфраструктуре.
