## Вывод для ближайшей итерации

Приоритет — **признаки переходов и длительности состояний + отдельные модели типов событий + ансамбль CatBoost/LightGBM**, проверенные на последовательных временных отрезках. TabM — обоснованный дополнительный кандидат, если простые ансамбли перестанут давать прирост. Foundation models следует испытывать на подходящем подмножестве, а не считать гарантированным решением.

Целевые Precision > 0.7 и Recall > 0.5 сформулированы в копии требований, но сами по себе не доказывают достижимость для любой выбранной цели. «Любая тревога завтра», «начало новой технической неисправности» и «неисправность с предупреждением минимум за сутки» — разные задачи. Их результаты нельзя смешивать в одной таблице улучшений.

Уверенность в приоритете признаков, целевой переменной и временной проверки — высокая; в приросте от ансамбля — средняя; в достижении двух порогов одновременно до эксперимента — низкая.

Позднее найден локальный оригинал ТЗ: §13 прямо предусматривает метеорологические данные через открытые API и РТЭК; общее разрешение на произвольные сторонние датасеты не сформулировано. Отсутствие запрета не приравниваем к официальному разрешению. Исследование открытых методов и самостоятельное использование уже предоставленных организатором справочников можно продолжать независимо от этого вопроса.

Локальные источники — [автоматическая SRT-расшифровка](../artifacts/transcripts/gorod_8_dzhkh.srt) и [подготовленный по ней Q&A](../artifacts/transcripts/gorod_8_dzhkh_qa_summary.md). У них нет статуса проверенного оригинала ТЗ:

- **41:20:** Q&A сообщает, что реальные координаты не предоставляются. Фактический CSV объектов содержит анонимные названия («Альфа», «Пси»), идентификаторы и иерархию, без широты/долготы.

Следствие: внешний эксперимент следует хранить отдельно, указывать происхождение, лицензию, допущения и эффект. Для метеоданных разрешение подтверждено оригиналом; для основной модели остаётся проверить качество привязки и историческую доступность конкретного продукта. Для произвольных сторонних датасетов общей формулировки нет.

### Как избежать утечки через погоду

Для каждой строки обогащения нужны `source`, `valid_time`, `issued_at/available_at`, версия продукта и координаты выбранной региональной точки. Соединение разрешает только записи с `available_at <= prediction_time`. Инициализация погодной модели и момент публикации прогноза различаются.

Фактическая температура/осадки будущего дня недопустимы. Реанализ ERA5/ERA5-Land также не следует автоматически считать оперативно доступным: он создаётся с задержкой и уточняет прошлое. Даже сдвиг на сутки без проверки задержки конкретного продукта недостаточен. [Документация Historical Weather](https://open-meteo.com/en/docs/historical-weather-api) описывает реанализ, а [Single Runs](https://open-meteo.com/en/docs/single-runs-api) — архив запусков, включая hindcasts.

Если время доступности старого продукта не подтверждено, можно провести исследовательскую оценку с явной пометкой «ретроспективный погодный контекст», но нельзя включать её результат в доказательство качества оперативного прогноза. Для воспроизводимого производственного варианта нужен архив реально опубликованных прогнозов/наблюдений либо сбор таких данных вперёд.

## План сравнения комбинаций

1. **Зафиксировать две оценки.** Сохранить исходную цель «тревога завтра» для честного сравнения с baseline. Отдельно определить новый эпизод технического состояния, правила слияния повторов, eligibility и момент выдачи. Для предупреждения не менее чем за сутки, например, признаки до конца D и начало события в D+2; событие D+1 является другой задачей.
2. **Сделать временные блоки.** Train → промежуток для проверки вариантов → отдельный период для порога → будущий test. Удалить строки обучения, чьи целевые окна пересекают следующую часть. Наблюдаемость определять по информации на момент выдачи; исчезновение журнала не означает исправность.
3. **Первая комбинация.** CatBoost и LightGBM на одной витрине; варианты `w*p_cat + (1-w)*p_lgb`, где w ∈ {0, 0.25, 0.5, 0.75, 1}. Сначала убедиться в одинаковом порядке строк. Вес выбирается до просмотра test. Само по себе усреднение коррелирующих моделей не гарантирует улучшение.
4. **Вторая комбинация.** К этим признакам добавить состояния и аномальность: давность/длительность неисправности, число переключений, burstiness, отличие от личной нормы и долю проблемных соседей. Норму/детектор обучать на прошлом; метапризнаки для train формировать временным cross-fitting. Сравнить add/remove групп признаков.
5. **Специалисты.** Для крупных типов датчиков/событий проверить отдельные модели с общим fallback. Не подбирать удачный тип на test; редкие группы могут проигрывать общей модели из-за малого числа эпизодов.
6. **Следующий вычислительный бюджет.** TabM на той же витрине. Chronos-2 — отдельный пилот для непрерывных рядов, только если хватает покрытия и есть понятное событие выхода из диапазона. TabPFN оставить резервом после проверки конкретных весов/ресурсов.
7. **Выбрать лучший операционный вариант.** Показывать AP и полную PR-кривую; отдельно maximum recall при P ≥ 0.7 и maximum precision при R ≥ 0.5 на validation. Если допустимых порогов нет, явно фиксировать отсутствие решения. Порог и модель замораживать, затем проверять один раз на test. При последующих итерациях уже просмотренный test становится сравнительным benchmark, а не нетронутой финальной оценкой.

Помимо строковых метрик нужны Precision/Recall начал эпизодов, медианное упреждение, ложные предупреждения на объект-день и число карточек в сутки. Неопределённость оценивать блочным bootstrap по времени/объектам. Произвольная коррекция всех точек эпизода после попадания в одну точку и выбор порога на тесте завышают доказательство качества.

**Практическая рекомендация:** в ближайшем прогоне комбинировать уже работающие бустинги, причинно доступные признаки состояний и контекст объекта. Внешнюю погоду и нейросети добавлять только как измеримые альтернативы. Число используемых методов не является целью; нужен воспроизводимый выигрыш на будущем периоде.
